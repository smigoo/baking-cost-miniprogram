# 烘焙成本小程序 · 产品拓展路线图

| 版本 | 日期 | 说明 |
|------|------|------|
| v1.0 | 2026-11-15 | 基于当前已落地的 4 页闭环（记销量 / 原料 / 商品 / 经营报表）+ 本地存储 + JSON 备份，输出拓展方向与优先级 |

> 本文所有判断基于当前工程实际能力与明确的目标人群特征，未引用第三方市场规模数据。文中数字凡为推算均标注「估算」。

---

## 一、一句话定位

**这是一个「个体烘焙经营者的成本与定价账本」，不是收银系统、不是进销存、不是社区。**

定位一旦漂移，功能就会失控。所有拓展必须回答一个问题：**它让这本账更准、更不会丢，还是让老板更容易做决定？** 两者之外的一律先不做。

---

## 二、现状能力盘点（已够用的 vs 真缺口）

| 层 | 已具备 | 真缺口（决定能拓展到哪） |
|----|--------|--------------------------|
| 数据 | 4 页完整闭环、本地持久化、JSON 备份/导入/快照撤销、深浅主题 | **单机**：换机、重装、手机丢了即归零；无自动版本历史 |
| 成本 | 原料单价（7 种质量单位 + 5 种体积单位）、配方、包装、人工、固定分摊、渠道费 | **进价靠手填且不会更新**，原料涨价后全店成本失真；无损耗/报废；体积单位靠 `1ml≈1g` 估算 |
| 定价 | 保本价 / 建议价 / 每单净赚 / 材料倍率 / 四态提示 / 毛利率预警下钻 | 只有「算完」，**没有「算完能直接拿去用」的产出** |
| 输出 | 今日长图 / 本月长图 | 无给客户的报价单、无给员工的成本卡 |
| 组织 | 单店单人 | 无多账本、无多店、无子账号 |

**关键结论**：功能不缺，缺的是**数据可信度**和**决策到行动的最后一公里**。

---

## 三、五条拓展主轴

### 轴 1｜数据可信层：从「能算」到「不会丢」（地基，必做）

| 项 | 内容 |
|----|------|
| 为什么 | 现在的备份是**手动**的。用户不会每周手动导一次，一旦丢数据，丢的不是数据，是信任。这一层不做，上面所有功能都建在沙子上 |
| 做什么 | ① 云同步（换机恢复、多端同源）；② 自动快照（每次大量改动前自动存一版，保留最近 N 版，可回滚）；③ 数据健康自检（配方引用了已删原料、单价为 0、库存负值等，一键列出） |
| 成本 | 高（需要服务端或云开发） |
| 判据 | 用户敢把 3 个月真实经营数据放进来 |

**⚠️ 这条有决策分叉，见第六节。**

---

### 轴 2｜成本动态化：从「记账」到「算得准」（差异化）

| 项 | 内容 |
|----|------|
| 为什么 | 烘焙最大的成本变量是原料价格，而现在的成本是一次性填死的。黄油从 40 涨到 60，全店商品定价立即失真，但工具不会告诉你 |
| 做什么 | ① **进价台账**：每个原料保留进价历史（日期 / 单价 / 供应商 / 采购量），当前单价取「最近一次」；② **涨价影响面分析**：录一次新进价 → 自动列出受影响的商品、成本涨幅、毛利率跌破警戒线的商品（这是最有价值的一屏）；③ **损耗记录**：报废/试做/赠品单独计量，不计入销量但计入成本，报表出「真实损耗率」；④ 体积单位密度表（面粉/糖/油/奶分别设密度，替代统一的 1ml≈1g） |
| 成本 | 中（纯本地数据模型 + 两个视图，无需后端） |
| 判据 | 用户每进一次货，愿意打开录一次 |

---

### 轴 3｜商务输出：从「算完」到「能卖」（最容易被感知价值）

| 项 | 内容 |
|----|------|
| 为什么 | 私房烘焙/小工作室的日常场景是：客户问「这个 6 寸多少钱」。现在得自己心算 + 翻记录。工具算得再准，不能变成一句报价就没闭环 |
| 做什么 | ① **报价单生成**：勾选商品 + 数量 + 折扣 + 备注 → 生成一张干净的图（复用现有 canvas 长图能力）→ 直接发客户；② **成本卡**：单品成本明细单页，给员工或合作方看（隐藏渠道费和净利率，只显示成本构成）；③ **阶梯报价**：同款按数量分档（如 1–5 个 / 6–10 个），团购场景 |
| 成本 | 低（canvas 已有，主要工作量在排版与模板） |
| 判据 | 用户一周内主动用了 ≥3 次 |

---

### 轴 4｜经营参谋：从「记录」到「建议」（加值层，别做太重）

| 项 | 内容 |
|----|------|
| 为什么 | 报表现在是「呈现事实」，老板要的是「所以我该干什么」 |
| 做什么 | ① **盈亏平衡点**：月固定支出 ÷ 平均每单毛利 = 本月至少要做多少单，显示「已完成 X%」；② **定价模拟器**：改时薪/产能/净利率，实时看全店利润变化，**不落库**（沙盒模式，按取消即还原）；③ **卖得动 × 赚得多** 四象限（现有排行只按单一维度排）；④ 单品建议动作（如「毛利率 12% 且销量前 3 → 建议提价至 X 或替换配方」） |
| 成本 | 中低（都是已有数据的重新聚合） |
| 判据 | 用户看完报表后有不只「知道了」的反应 |

---

### 轴 5｜供应链与生态（Won't，现阶段明确不做）

原料集采、配方市场、达人分成、社区分享。原因：重运营、需要 BD 与履约、跨品类、内容有版权风险。**这是平台玩法，个体工具早期碰它必死。** 记入后续版本池，不排期。

## 四、优先级与取舍

按 MoSCoW 收口，成本按「改动面 / 是否需后端」估，非人日承诺。

| 优先级 | 能力 | 所属轴 | 成本 | 为什么是这个位置 |
|--------|------|--------|------|------------------|
| **Must** | 自动快照 + 数据健康自检 | 1 | 低 | 不改数据层架构就能做，先把「不会丢」的一半补上，性价比最高 |
| **Must** | 进价台账 + 涨价影响面 | 2 | 中 | 唯一能形成「别人抄不走」的点：它建立在你的配方数据上 |
| **Must** | 报价单生成 | 3 | 低 | 复用 canvas，用户可感知价值最强 |
| **Should** | 云同步 / 多端 | 1 | 高 | 产品化前提，但需要先定技术路线（见第六节） |
| **Should** | 盈亏平衡点 + 定价模拟器 | 4 | 中低 | 数据现成，纯聚合 |
| **Should** | 损耗记录 | 2 | 低 | 数据模型加一张表，报表加一行 |
| **Could** | 成本卡、阶梯报价 | 3 | 低 | 报价单的延伸 |
| **Could** | 商品/原料「软停用」替代硬删 | — | 低 | 已留口，早做早安生（硬删会连带清历史销量） |
| **Could** | 多账本（烘焙/咖啡/其他） | — | 中 | 有跨品类需求再做 |
| **Won't** | 收银 / 支付 | — | — | 合规红线：需支付资质，且会把工具变成 POS，超出定位 |
| **Won't** | 完整进销存（库存、批次、盘点） | — | — | 个体经营者学不动，会劝退主要用户 |
| **Won't** | 供应链集采 / 配方市场 | 5 | — | 重运营，非工具层能力 |

**推荐执行顺序**：自动快照 → 数据健康自检 → 进价台账 → 涨价影响面 → 报价单 → 云同步 → 盈亏平衡点 → 定价模拟器。

前三步都是本地改造、无后端依赖、可独立上线，做完就有底气谈「产品」；云同步是唯一需要外部决策的，单独拉一条线。

## 五、要不要真的做成产品（结论）

**可以做，但要把预期定准。**

- **人群**：私房烘焙、小型工作室、家庭作坊转型的小店。精准但天花板有限，属于「小而深」的工具。
- **护城河**：不是算法（成本公式谁都能写），而是**数据沉淀**。用户录满 3 个月配方、进价历史、销量后，迁移成本极高。所以拓展的第一优先级永远是「让数据更值得沉淀」（轴 1 + 轴 2），而不是加更多功能入口。
- **变现路径**：基础功能免费（算成本、看报表、手动备份）→ 订阅制开放（云同步多端、报价单无水印、涨价提醒、多账本）。不做一次性买断，订阅能对齐持续服务成本。
- **主要风险**：同类「成本计算器」小程序多且免费；用户留存依赖「持续录入」这一动作，一旦中断就流失。对策是把录入成本压到最低（扫码录入进价、历史记录一键复用、语音/文本批量导入已在备份里具备基础）。
- **不建议**：做通用型「小店经营管理平台」。一旦扩品类（零售、餐饮、手作），成本模型就要重写，现有优势归零。

## 六、需要拍板的一个决策点：数据层往哪走

这是唯一会卡住整条路线的岔口。

| 方案 | 做法 | 优点 | 代价 | 适用 |
|------|------|------|------|------|
| A. 维持本地 + 强化备份 | 只做自动快照、健康自检，备份走微信文件 | 零成本零运维，符合当前零后端架构，一天不用改架构 | 换机体验差，长期是天花板 | 先自用 / 小范围试用 |
| B. 微信云开发 | `wx.cloud` + 云数据库 + 云函数 | 最快落地（无需服务器与鉴权）、免运维、天然多端 | 绑定微信生态、按量计费、数据导出受平台约束 | 想快速验证产品化 |
| C. 自建后端 | 复用现有 Node/ECS 能力，自建账号与同步 | 完全可控、可做 PC 网页版、数据自主 | 要写鉴权/加密/备份策略，有持续运维成本 | 确定要做成正式产品 |

**建议**：先 A 补「不会丢」的一半（自动快照 + 健康自检，两周内可完），同时用 A 收集真实使用反馈；确认有人持续用之后，直接跳 C 而不是 B——因为这个工具的核心资产是用户经营数据，长期看数据自主权比省事更重要。B 适合做短期验证，但迁出来的成本会二次支付。

## 七、里程碑建议

| 阶段 | 内容 | 完成标志 |
|------|------|----------|
| M1（本地增强，无后端） | 自动快照 + 数据健康自检 + 软停用替代硬删 | 用户任何误操作都能回滚 |
| M2（成本动态化） | 进价台账 + 涨价影响面 + 损耗记录 | 录一次新进价，能看到全店受影响商品清单 |
| M3（商务输出） | 报价单生成（+ 成本卡） | 客户问价，30 秒内出图 |
| M4（数据可信） | 按第六节决策落地同步方案 | 换手机不丢数据 |
| M5（经营参谋） | 盈亏平衡点 + 定价模拟器 + 四象限 | 报表能回答「这个月还差多少单回本」 |

---

## 八、本次不做什么（防范围蔓延）

- 不做收银、支付、外卖对接（合规与定位双重不匹配）
- 不做库存批次与盘点（向 ERP 滑坡的起点）
- 不做社交、内容分享、配方市场
- 不做多品类通用化（成本模型会崩）
- 桌面端 / 网页版在 M4 之后再评估，当前不排期
