# 烘焙成本测算小程序（微信原生）

把交互原型「烘焙成本-圆形图表.html」落地为可运行的微信原生小程序。零后端、零费用，数据用 `wx.setStorage` 本地持久化（换机/重装会清空，单机使用足够）。

## 工程结构

```
baking-cost-miniprogram/
├── app.js / app.json / app.wxss      # 应用入口、页面与 tabBar 注册、全局样式与 CSS 变量
├── project.config.json               # 微信开发者工具工程配置（公共配置，不含 appid）
├── project.config.sample.json        # 克隆后复制为 project.config.json 并填入自己的 appid
├── project.private.config.json       # 本地私有配置（含个人 appid，已 .gitignore，不入库）
├── sitemap.json
├── utils/store.js                    # 数据层：状态 / 持久化 / 单位换算 / 成本计算 / 各页 mutator
├── utils/recipe-book.js              # 配方手册纯计算层：按商品拆行小计+占比、按原料反查（不读写存储）
├── utils/canvas-kit.js               # 长图绘制原语：圆角卡 / 文字截断 / 瀑布图 / 逐日柱 / 进度条 / 环形 / 排行条
├── utils/export.js                   # 长图导出与分享：canvas → 图片 → 相册 / 微信分享面板
├── utils/backup.js                   # 备份文件读写：临时文件、分享、选文件、剪贴板
└── pages/
    ├── daily/                        # 记销量：日历选天 + 当日收支环形图 + 商品销量录入（从库选择）
    ├── material/                     # 原料：进价/重量/单位切换，自动算每克单价
    ├── goods/                        # 商品：配方手风琴、切换原料同步单位、售价/损耗、配方手册入口

```

## 如何运行

1. 用**微信开发者工具** → 导入项目 → 选择本目录 `baking-cost-miniprogram`。
2. AppID：仓库不携带任何 appid（`project.config.json` 为公共配置，不含 appid）。克隆后有两种方式：
   - **用自己的号**：把 `project.config.sample.json` 复制为 `project.config.json`，填入自己的 appid；或直接在开发者工具「详情 → 基本信息」里选号（会写入本地 `project.private.config.json`）。
   - **只想先看效果**：在开发者工具里选「测试号」，无需真实 appid。
3. 编译后即看到 4 个底部 Tab：记销量 / 原料 / 商品 / 经营报表（经营报表在最后，符合"先做后看"节奏）。
4. 无 npm 依赖、无后端、无云开发，零部署。

改完 WXML / 输入逻辑 / 长图 / 配方计算建议跑下面六个校验（分别防：循环别名取空导致卡片变空白、模板引用数据层没有的字段导致渲染崩溃、示例数据售价与成本互相对不上导致一进页面全是红字、输入框被 setData 回写成旧值导致「打不了字」、长图末块被截、配方金额口径漂移）：

```bash
node tools/check-wxml.js               # 标签平衡 / 循环别名 / wx:key 字段是否存在
node tools/check-render-contract.js    # 模板引用的 g.pricing.* 字段数据层是否真产出

# 六者都支持传目录

node tools/check-render-contract.js <工程目录>
```

## 建议售价（定价决策）

「成本算准了，然后呢？」这一步给答案。**不新增页面**，直接挂在已有的「售价」字段上：卡头下方常驻一条状态色提示条，把**你填的售价**和**保本价 / 建议价**直接对比。

### 成本口径（5 项，逐项可核对）

| 项 | 来源 | 说明 |
|---|---|---|
| 材料 | 配方 × 单位换算 × 单价 | 复用 `calcGood()`；再乘 `1 + 损耗率`（复用商品级 `lossRate`，不另建全局损耗） |
| 包装 | 商品级字段 `packCost`（元/件） | 同样乘 `1 + 损耗率`；蛋糕盒、丝带这类最容易被漏掉 |
| 人工 | 商品级 `laborHours` × 全局时薪 | 私房主最大的隐性成本 |
| 固定分摊 | 现有 `fixedCosts` 合计 ÷ 全局月产能 | 与月报表口径**不同**，见下方注意 |
| 渠道费 | 售价 × 全局渠道费率 | 微信支付约 0.6% |

### 公式（渠道费会形成循环依赖，必须同时扣两项）

```
C_其他 = 材料 + 包装 + 人工 + 固定分摊
保本价 = C_其他 ÷ (1 − 渠道费率)
建议价 = C_其他 ÷ (1 − 目标净利率 − 渠道费率)     ← 分母同时减净利率与费率
理想价 = 建议价 × 1.1
```

- 售价舍入**只向上取到 0.5 元**（`roundHalfUp`）。向下取整会让建议价跌破保本价，绝对不允许。
- 稳利率 + 费率 ≥ 90% 时不给建议价（分母趋零会算出天价），参数入口也会把净利率收敛到 ≤ 95%、费率 ≤ 50%。

### 提示条四态

| 状态 | 判定 | 显示 |
|---|---|---|
| 定价健康（橄榄绿） | 售价 ≥ 建议价 | 建议 ¥x |
| 定价偏低（蜂蜜黄） | 保本价 ≤ 售价 < 建议价 | 保本 ¥a，建议 ¥b |
| 低于保本（砖红） | 售价 < 保本价 | 每单亏 ¥x |
| 未定价 / 待补全（灰） | 售价为 0 / 材料成本为 0 / 参数越界 | 建议 ¥x / 先补原料单价 |

### 参数放哪

- **全局**（时薪 / 月产能 / 目标净利率 / 渠道费率）：经营报表页「定价参数」卡，紧接固定支出——因为「月产能」和「固定支出」回答的是同一类问题。
- **商品级**（包装耗材 / 工时）：各商品卡点开定价明细后填。
- 缺项时按 0 计算但**必须显式标注「未填」**，不静默当 0.00，避免用户拿着偏低的价去卖。

### ⚠️ 两套固定成本口径不要混用

- 月报表：`fixedTotal × 已记录天数 ÷ 月天数`（`monthAgg`，随时间推进折算）
- 定价分摊：`fixedTotal ÷ 月产能`（`calcPricing`，按产量折算）

定价计算**绝不能**引用 `monthAgg().fixed`：月底只有几天记录时，那会把单件固定成本放大数倍。

### 数值示例（虚构，仅说明口径）

材料 8.5、损耗 5%、包装 2、时薪 30、工时 0.5h、月固定支出 2500、月产能 100、净利率 40%、费率 0.6%
→ 材料 8.93 + 包装 2.10 + 人工 15.00 + 固定分摊 25.00 = 51.03
→ 保本价 51.33，建议价 **86.00**（51.03 ÷ 0.594 = 85.90，上取 0.5），按建议价卖每个净赚 34.40

## 长图内容结构

只有**月报长图**。日报曾有一版，但单日数字小、没有对外传播价值，且「导出」按钮独占一整行干扰记销量主流程，已移除；日报回归纯录入页。

长图不是「把页面上的数字搬到画布上」。页面用于操作，长图用于**让看的人三秒抓住结论**——所以文字罗列一律换成图表。

实现上分两遍（`buildReport()` 算布局 → `drawReport()` 按同一份 `blocks` 绘制）：每个区块的绘制函数与它的高度绑在一起，总高一并算出。原先是估高度（`H = 360 + n*44 + 120`），加一个区块必然出现「末块被截」或「底部大片留白」。绘制原语统一在 `utils/canvas-kit.js`（圆角卡、文字截断、瀑布图、逐日柱、进度条、环形、排行条）。

### 月报长图（约 750 × 1700）

| 区块 | 内容 |
|------|------|
| 深棕 hero | 标题 + 月份 + 数据完整度（记录 24/30 天）+ **本月净利大数字** + **盈亏平衡进度条**（已回本超出 N 单 / 还差 N 单） |
| 核心指标 | 营收 · 毛利 · 毛利率 横排三卡，右上带营收环比 |
| 收支去向 | **瀑布图**：营收 → 减材料 → 减固定 → 净利 |
| 逐日毛利 | 当月每天一根柱，底部灰条＝当天没记销量（漏记一眼可见） |
| 赚钱排行 | 前 6 名按毛利排序，毛利率 < 30% 标红（卖得动但不赚钱的品） |
| 低毛利预警 | 低于 30% 的商品**逐个列名**（原来只写「N 个」，等于没给信息） |
| 固定支出 | 逐项明细 + 合计 |

### 口径说明

- **盈亏平衡用「整月固定支出总额」**，不用按已记录天数折算后的 `fixed`。后者分母随记录天数变化，目标单量会天天飘，用户没法拿它当经营目标。
- **环比/对比在上期无记录时直接说「暂无可比」**，不硬算百分比（否则会给出 +100% 这类误导）。
- 长图主题跟随系统（与页面一致）。若要固定浅色（朋友圈白底信息流下更亮），改 `drawReport` 前的 `getPalette()` 入参即可。

### 已知边界

- 商品名过长自动截断加省略号（`clipText` 按像素测量，不按字数估）。
- **店铺落款区（店名/联系方式/二维码）尚未做**：需要先在设置里加店铺信息字段，且二维码要真实小程序码素材，不能用占位图凑。

## 配方手册（只读总览）

入口：商品页顶部「配方手册 ›」（`pages/recipe/recipe`，非 tab 页，返回即回到商品页）。

解决的是三个具体不便：商品卡一次只能展开一张，没法横向比配方；配方行只有「原料+用量」，看不出**每行花了多少钱**；没有按原料反查的路径，答不了「黄油涨价我哪几个商品受影响」。

### 两个视图

| 视图 | 每张卡显示 | 排序 |
|------|-----------|------|
| 按商品 | 商品名 + 单品成本；每行 = 原料名 / 用量 / 小计金额 / 成本占比条与百分比；底部 = 材料合计 + 损耗加成 + 成本 | 行按**小计金额降序**，成本大头自动顶到最上 |
| 按原料 | 原料名 + 单价（元/kg）；被几个商品使用、共花多少钱、合计用量；逐个列出各商品的用量与小计 | 卡按**使用次数降序**，闲置原料沉底但仍显示 |

### 口径（三条，勿混用）

1. **单行小计** = 每克单价 × (用量 × 单位换算系数)。单位换算统一走 `store.UNIT_FACTOR`（以克为基准的单一事实源），本页不另立换算表。
2. **材料合计** = 各行小计相加（不含损耗）；**成本** = 材料合计 × (1 + 损耗率)，与 `store.calcGood` 完全一致。占比条分母是**材料合计**（不含损耗），所以各行占比之和恰为 100%。
3. **元/kg 折算** = 每克单价 × 1000，只为让不同原料的单价能横向比；原料页展示的采购口径（元/采购单位）不变。

### 边界行为

| 情况 | 表现 |
|------|------|
| 配方行引用的原料已被删除 | 行显示「原料已删除」标红，小计 0，不静默丢行 |
| 配方行还没选原料 | 显示「未选原料」标红，小计 0 |
| 用量为 0 或空 | 小计 0，**条宽 0**（不画假进度条误导） |
| 商品无配方 | 卡片提示「还没配原料 —— 去配」，点击跳回商品页并展开该卡 |
| 原料无任何商品使用 | 「暂无商品使用」，卡片保留不隐藏 |
| 还没商品 / 还没原料 | 全页空态 + 一键跳对应 tab 页 |

### 为什么是只读页

写入口只保留在商品页。同一份配方若有两个可写入口，会出现「改完不知道以谁为准」的状态分叉；手册的职责是**算清楚 + 看得懂**，不是第二编辑器。

## 数据备份与恢复（防丢）

数据只存在本机微信里：换手机、卸载重装、清理存储都会清空，所以必须有一条「导出到用户自己手里」的路，以及一条「能导回来」的路。入口在**经营报表页 → 数据备份**。

### 备份包含什么

一份备份 = 全量快照，五类数据一起走，缺一项恢复后算出来的成本与报表就是错的：

| 内容 | 说明 |
|---|---|
| `materials` | 原料（id / 名称 / 价格 / 规格数量 / 单位） |
| `goods` | 商品（id / 名称 / 售价 / 损耗率 / 包装 / 工时 / 配方行） |
| `fixedCosts` | 固定支出项 |
| `daily` | 每日销量（`YYYY-MM-DD` → 商品 id → 数量） |
| `settings` | 定价参数（时薪 / 月产能 / 目标净利率 / 渠道费率） |

配方行引用的是原料 `id`，而原料 id 也在备份里 —— 这是「恢复后成本不会变 0」的前提，有回归断言守着。

备份文件形如 `烘焙成本备份-20261115-1820.json`，结构为 `{app, schema, exportedAt, counts, data}`。

### 导出（两条路，按环境自动降级）

1. **导出备份文件**：写入小程序用户目录 → 调起 `wx.shareFileMessage` 发送给朋友/文件传输助手。发出后文件就存在你自己的聊天里，长期有效，不受本机缓存影响。
2. **复制备份文本**：当前环境不支持发送文件（部分基础库/开发者工具）时自动降级；也可手动点它。注意聊天输入框粘贴超长文本可能被折叠，建议粘到备忘录或文件传输助手。
3. 导出前清理旧的备份文件，只留最新一份（备份本身很小，但没必要堆积）。

### 导入（先预览，再选模式）

1. **从聊天选择备份文件** → `wx.chooseMessageFile` 选 `json`
2. **粘贴文本导入** → 读剪贴板
3. 校验通过后先报数：`备份时间 + 含 N 原料 / N 商品 / N 项支出 / N 天销量`，同时对比现有条数
4. 选模式：
   - **覆盖导入**：用备份整体替换现有数据（破坏性，额外一次二次确认，确认按钮红色）
   - **合并导入**：保留现有，只补备份独有；同 id 的原料/商品、同「名称+金额」的固定支出、同一天的销量一律跳过，不覆盖本机真实数据
5. 完成后弹出结果（新增/跳过各多少），并出现「撤销上次导入」

### 撤销与快照

- 每次导入前自动写一份快照到 `baking_state_snapshot_v1`，含当时的五类数据
- 快照写入失败时**直接取消导入**（宁可不导入，也不让现有数据没退路）
- 「撤销上次导入」把数据恢复到快照状态；撤销时会把「撤销前」的数据也存成快照，**撤销本身可反悔**
- 快照只保留最近一份，每次导入覆盖

### 清洗规则（导入的数据可能来自老版本或手改文本）

| 情况 | 处理 |
|---|---|
| 不是合法 JSON / 空内容 | 拒绝，提示可能复制时被截断 |
| `app` 字段不是本小程序 | 拒绝，并显示来源 |
| 既无 `materials` 也无 `goods` | 拒绝（不像备份） |
| 只给了 `data` 本体没有外层包装 | 兼容（用户手抄场景） |
| 金额/数量为负数或非数字 | 收敛为 0 |
| 单位不在 `UNIT_FACTOR` 里 | 回落为 `g` |
| `recipe` 不是数组 | 修正为 `[]` |
| 配方行 `m` 为空 | 保留（用户可能正填一半） |
| 日期非法（如 `2026-13-99`） | 剔除（正则通过不算数，按真实日历校验） |
| 净利率 > 95% / 费率 > 50% 或为负 | 收敛到边界值 |
| 备份内部 id 重复 | 重新分配 id（防「一删删一批」老坑复发） |
| 老存档缺 `settings` / `packCost` / `laborHours` | 补默认值 / 补 0，导入后成本照常可算 |

> 隐私：整个备份/导入过程**不联网、不上传**，文件只写在小程序用户目录并由用户自己发到聊天里。备份内容含你的成本与售价，属于经营数据，建议只发给自己。

## 数据持久化

- 存储键：`baking_state_v1`（含 materials / goods / fixedCosts / daily / settings）。**不要改这个键名**，改了等于把老用户数据全部丢弃。
- `settings`（定价参数）是后加字段：老存档没有时 `init()` 按 `PRICING_DEFAULT` 补齐并补存一次；商品缺 `packCost`/`laborHours` 时 `getState()` 统一补 0，老数据不会崩。
- 首次启动写入样例数据（4 原料、3 商品、含 1 个未来日演示预估），之后所有改动自动落盘。
- 空白商品自动收敛：`store.pruneBlankGoods()` 在启动与每次进入商品页时执行，清理「无配方、无销量、未填名字/售价」的历史空壳并写回存储，最多保留 1 张待填草稿；有配方 / 记过销量 / 填过名字+售价的商品一律保留。幂等，收敛后不再写盘。
- **删除为精确单条**：商品/原料删除按 `findIndex` + `splice` 只移除 1 条，返回实际删除条数（0/1）；id 为空或找不到时拒绝删除并返回 0，页面给出明确提示。禁止用 `filter(x => x.id !== id)`——id 缺失/重复时会一次删掉一批。
- **id 自愈**：`store.ensureUniqueIds()` 在启动时把历史存档中 id 缺失、重复、数字类型的商品修正为唯一非空字符串 id（数字转字符串以对齐 WXML dataset 类型），保证所有按 id 的操作都是精确单条；新增/复用草稿时也会调用一次，防止返回空 id。
- **存档判定看整体**：`init()` 只要存档里存在 materials / goods / daily 任一字段就视为有存档并原样载入；仅当完全无存档时才写入样例数据。避免「原料全删光后重进」把商品与销量一起重新 seed 掉（数据丢失）。
- **加原料有明确结果**：`store.addRecipe()` 返回配方行 / `'NO_GOOD'`（商品不存在）/ `'NO_MATERIAL'`（原料库为空）。成功时新增行 **`m: ''` 表示「尚未选择原料」**（页面显示可点击的「选择原料 ▾」下拉，由用户自己选，避免默认塞第一种原料被误认成静态文字；未选的行不参与成本计算）。原料库为空时不写无效行（那种行 picker 无选项、成本恒为 0，表现为「加了但选不到原料」），页面改为弹窗引导去原料页。
- **`picked` / `missing` 两个标记区分三种状态**：未选择（`picked=false, missing=false`，显示「选择原料 ▾」）／ 已选择（正常显示原料名）／ 已选但原料被删（`picked=true, missing=true`，砖红「原料已删除·重选」）。
- **内存/存储兜底重载**：`store.reloadFromStorage()` 仅在「内存里商品或原料对不上」的异常状态下调用（如 `addRecipe` 前发现原料库空），先以存储为准重载一次再判定，杜绝「原料页明明有原料、商品页却说没有」的误拦截。
- **孤儿配方只标记不删除**：配方行引用的原料被删除后，该行仍然保留原数据，`getState()` 给出 `missing: true`，页面显示砖红色「原料已删除·请重选」；不做静默删除，避免二次数据丢失。
- **页面层 id 兜底**：商品页 `refresh()` 过滤掉无 id 的数据项，只渲染合法卡片；所有卡片操作通过 `resolveGid(e)` 解析 id（`data-gid` 优先，`data-gi` 列表索引兜底，其次 `target.dataset`，最后「页面上唯一展开的卡」）。解析失败时自动刷新一次并提示，不静默失败、不误删。
- 想清空重来：微信开发者工具 → 调试器 Console 执行 `wx.clearStorageSync()`，或「清缓存」后重启。**这会连备份快照（`baking_state_snapshot_v1`）一起清掉**，清之前请先导出备份。
- 备份快照键：`baking_state_snapshot_v1`（每次导入前自动写入，用于「撤销上次导入」）。

## 与原型 / 平台差异（已在交付前确认）

1. **tabBar 已用自定义图标**（`images/tabbar/tab-*.png`，162×162 单色：常态深暖棕 `#4A3B2E`、选中主题黄 `#FFC400`），与原型视觉一致；文字仍由系统 tabBar 渲染，无需自定义 tabBar 组件。
2. **环形图用 CSS `conic-gradient`** 实现（小程序无内联 SVG 标签），视觉接近原型；极老基础库不支持时降级为纯色圆，不影响功能。
3. **PDF 改为长图**：小程序无法原生生成 PDF 或直发朋友圈。标准做法是用 canvas 绘制长图海报，再「保存相册」或用 `wx.showShareImageMenu` 调起微信分享面板（可选好友/朋友圈）。这是平台能力边界，非功能缺失。
4. **删除为硬删**：商品/原料删除会同步清除相关历史销量（与原型一致）；正式上线前建议改为「停用/归档」以保留历史，已在产品层面留口。
